# MIZUNO PHOTO MEMBER — Phase 2 MEMORY Sync Contract

Baseline: 2026-09-24 JST

## Goal

When an existing MIZUNO PHOTO customer creates a Member account, safely reconstruct the customer's already completed photography history as MEMORIES without fuzzy identity matching, duplicate memories, or cross-family exposure.

## Canonical sources

Customer CRM remains the source of truth for customer identity and historical reservation evidence.

- customer identity: `customers.customer_id`
- historical shoots: `customer_reservations`
- completed-shoot semantics: existing `crm-reservation-status-contract.mjs`
- Amazon Photos delivery links: `customer_delivery_links`
- Member household boundary: explicit Customer ID -> Family ID link from Phase 1

The Member app does not infer history from customer name, address, phone, email, LINE display name, or similar text.

## Historical MEMORY candidate rule

A reservation may become a MEMORY candidate only when:

1. its exact `customer_id` equals the authenticated canonical Customer ID;
2. it has a stable `reservation_id`;
3. its latest reservation state is a completed-shoot state under the existing CRM status contract; or
4. it is a legacy customer CSV shoot row with the controlled CSV reservation identity already generated by CRM.

Cancelled, future, ambiguous, soft-deleted, or unstable-ID rows are not imported.

## Amazon Photos

A delivery URL is attached only when:

- the delivery row belongs to the same exact Customer ID;
- `provider = amazon_photos`;
- the URL is HTTPS;
- the delivery row's `reservation_id` exactly equals the MEMORY source reservation.

Customer-level fallback to an unrelated delivery URL is prohibited.

## Family authorization

The future Member session provides its server-verified Family ID.

Before any MEMORY history is returned or synchronized:

1. resolve the exact canonical Customer ID;
2. resolve its explicit active Family ID;
3. require the session Family ID to equal that Family ID;
4. otherwise return access denied.

Family A must never receive Family B's source history.

## Idempotency

The durable source key is:

`customer-crm:reservation:<reservation_id>`

The future Member Core enforces one MEMORY for each `source_system + source_reservation_id`.

Re-running account setup or historical synchronization therefore returns existing MEMORIES instead of creating duplicates.

Conflicts fail closed when:

- a source row unexpectedly belongs to another Customer ID;
- the same source reservation appears more than once in one source batch;
- an existing MEMORY for that reservation belongs to a different Family ID;
- an existing MEMORY for that reservation belongs to a different source Customer ID.

## Member Core schema source

This phase adds source-only schema for:

- `member_memories`
- `member_memory_media`

Representative app photos are referenced by private `storage_key`; photo binaries are not placed in D1.

The schema source is not applied to Production in this phase.

## Read-only plan API

The foundation provides a future internal contract:

`GET /api/internal/member-memory-plan/family/:family_id/customer/:customer_id`

It performs authorization and calculates:

- `to_create`
- `already_synced`
- `skipped`
- `conflicts`

It performs zero writes.

## Current phase exclusions

Not included yet:

- Production migration apply
- Production D1 writes
- actual MEMORY insertion
- Member customer-facing route wiring
- photo binary storage
- R2 upload
- HOME / MEMORIES UI
- LINE Login activation
- Google Sheets backup execution
- Production deploy

## Next gate

Before any write implementation:

1. this read-only source/plan foundation must pass CI and review;
2. cross-family denial tests must pass;
3. idempotency tests must pass;
4. the Member Core migration needs separate Production schema approval;
5. the first historical sync write path needs separate Production D1-write approval.
